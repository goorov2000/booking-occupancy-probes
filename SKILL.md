# /glamping-occupancy — снимок загрузки глэмпингов

> **Примечание витрины.** Это инструкция агенту из рабочего репозитория,
> перенесённая в самостоятельный проект без правки содержания. Пути кода
> заменены на `occupancy/…` и `tests/…`; имя заказчика — на роль. Каталоги
> данных исследования (`agent-runtime/…`, `docs/research/…`) и внешний
> пакет `cf` (Run Log, транспорт телеграма) в витрину не входят — форматы
> файлов описаны в SCHEMA `occupancy/occupancy_core.py`, см. README.

Гибрид из двух звеньев (спека: `docs/spec.md`):

- **Пробник** — детерминированный Python без браузера и без агента:
  `.venv/bin/python occupancy/cli.py --probe <username>`
  воспроизводит рецепты из реестра и пишет датированный снапшот.
- **Разведчик** — ты, агент с браузером. Работаешь только с объектами
  БЕЗ рецепта или с рецептом `broken`. Итог разведки — рецепт в реестре,
  который дальше гоняет пробник; сам ты загрузку не пересказываешь.

Файлы (правило №4 — runtime-артефакты в `agent-runtime/`; сам каталог в витрине отсутствует,
формат каждого файла — SCHEMA (а)/(б)/(в) в `occupancy/occupancy_core.py`):

- Реестр рецептов: `agent-runtime/research/glamping/occupancy/recipes.json`
  (формат — SCHEMA (а) в `occupancy/occupancy_core.py`; это ГЛАВНЫЙ ШОВ фичи).
- Цели: `agent-runtime/research/glamping/occupancy/targets.json` (правится руками).
- Снапшоты: `agent-runtime/research/glamping/occupancy/snapshots/<YYYY-MM-DD-HHMM>/`.

## Машинная разведка: сначала scout, агент — только на остаток

С 04.09 опознание движка и добыча параметров рецепта — детерминированный код:

    .venv/bin/python occupancy/scout.py \
        --url <сайт> --key <ключ цели> [--allow-post] [--budget 12]

Разведчик читает страницы `/`, `/booking`, `/bron`, ищет маркеры всех шести
движков (не первый попавшийся — список), достаёт главный параметр из того же
HTML и союзом 2-3 пар дат в разных месяцах собирает справочник юнитов. Выход —
черновик рецепта в `agent-runtime/research/glamping/occupancy/scout-out/<ключ>.json`
с тремя честными исходами: `high` (движок один, параметры добыты), `low`
(движок опознан, чего-то не хватает — список в `missing_params`), `refuse`
(движка нет / антибот / ДВА сильных маркера разных движков — решает агент).
В `recipes.json` scout не пишет никогда: рецепт попадает в реестр только после
проверки пробником (шаг 5 ниже).

Замер 04.09: 54 самарских сайта за 5,8 минуты, 34 готовых рецепта, 3 `low`,
17 `refuse`; на доразведку агентом ушло 11 объектов. Подсказка движка из
внешних таблиц — не факт: у 9 объектов из 54 она оказалась ложной.

Ручная разведка ниже — для исходов `low` и `refuse`. Всё, что там написано про
маркеры и параметры, scout уже умеет; читать это нужно, чтобы понимать, ЧТО он
сделал и где мог ошибиться (справочник юнитов не гарантированно полон — сверка
с числом домиков на сайте остаётся за агентом).

## Разведка объекта

Строго ОДИН объект за раз. Параллельных разведок в одном браузере не бывает:
гонки вкладок — доказанные грабли прогона 11.08 (рефы элементов протухали
между снапшотами, объекты терялись). Закончил объект — записал рецепт —
только потом следующий.

### Шаг 1. Найти сайт

По убыванию доверия:
1. `agent-runtime/research/glamping/master-table.json` (в витрине отсутствует) — ключ «Сайт» у строки
   объекта (секции msk/far; username — в ссылке «Instagram»).
2. Био Instagram (`instagram.com/<username>`): ссылка, taplink, linktree.
   Taplink разворачивай: внутри обычно и лежит настоящий сайт.
3. `agent-runtime/research/glamping/calendars-out/<username>.json` (в витрине отсутствует) — поле
   `site` и `probe_results` прошлого прогона (там же — уже опознанный движок).
4. Веб-поиск по названию объекта + гео. Волна 2 трижды записала «сайта нет»
   там, где он был (istramagicclub.ru, domdal.ru, woodglamp.site) — не
   доверяй старому вердикту «нет сайта», проверь поиском сам.

Сайт может «редиректить» на чужой домен глюком хостинга (11.08:
baninaozerah.ru «уводил» на podnebom.camp, а podnebom.camp разок отдал
контент novo-okatovo.ru) — перепроверь вторым заходом, прежде чем верить.

**Адрес в реестре — подсказка, а не факт: у broken-объекта проверяй его
первым.** Переразведка 09.09.2026: из десяти «маркеров модуля нет» ЧЕТЫРЕ
оказались не про объект, а про адрес — `telegram.im` вместо lesglamping.ru,
`old-sivukh.su` (chatium-витрина) вместо old-sivukh.ru, `volna-tlt.ru`
(домен ушёл чужому бизнесу) вместо volna.house, `adygea-otdyh.ru`
(припаркован в Timeweb) — нигде. Плюс `dom-shalash-na-use.tb.ru` без
страницы `/main` даёт 404 на всех трёх страницах разведки. Признаки, что
адрес не тот: мессенджер или витрина конструктора вместо сайта, 404 на
корне при живом домене, парковочная страница хостера, чужое название в
контактах.

**Модуль бывает НЕ ВСТРОЕН в сайт.** «Бронируй Онлайн» умеет hosted-страницу
`bronirui.online/<слаг>`: кнопки сайта уводят туда, и `znmsWidget.init` в
HTML сайта нет вовсе — scout честно скажет «маркеров нет». moduleId лежит в
HTML самой hosted-страницы, а Referer/Origin рецепта берутся её (домен
доверенный у движка). Прецеденты 09.09: smr_scandi_house (4282),
smr_baza_otdyha_privole (7691), раньше — vlesu_glamping.

### Шаг 2. Опознать движок по маркерам в HTML

Скачай HTML сайта (и его страницы `/booking`, `/bron`, «Забронировать»)
обычным HTTP-запросом с браузерным User-Agent и ищи маркеры:

| Движок | Маркеры в HTML |
|---|---|
| travelline (TL Integration) | `travelline`, `tlintegration`, context `TL-INT-<имя>_<дата>`, `?tl-booking-open=true` |
| bnovo (= reservationsteps) | `widget.reservationsteps.ru`, конструктор `BookingIframe({uid})`, `bnovo` |
| bronirui («Бронируй Онлайн») | `bronirui.online`, `bronirui-online.ru`, `znmsWidget.init({moduleId})` |
| litepms | `litepms.ru/widget/calendar?id=…` |
| homereserve (= realtycalendar) | `homereserve.ru/widget.js`, `initWidgetSearch({token})` |
| uhotels (виджет artDg) | `api.uhotels.app`, `adg-booking-widget`, `w.artDg`, токен отеля вида `<id>:<hash>` |
| кастом/чужой движок | `livewire` (Laravel), прочее без маркеров выше |

Кастомный или чужой движок = модуль ЕСТЬ, но пробника v1 нет: пиши рецепт со
`status: "broken"`, `engine: "custom-<движок>"` и `broken_reason` «движок …
не поддержан v1» (прецедент в реестре: lafa_club).
Маркеров нет вообще (только лид-форма/мессенджер) → ветка агрегаторов ниже.

**Маркеры двух движков разом — норма, и один из них может быть мёртвым.**
16.08 на pineriver.ru нашлись маркеры TravelLine (context
`TL-INT-pineriver_2022-08-26`, hotel_code 6086) — и они резолвились, но API
отвечал «Online booking of hotel # 6086 is temporarily unavailable» и пустым
календарём: это хвост 2022 года, оставшийся в вёрстке. Живая бронь шла через
UHotels на `/booking`. Поэтому опознание движка не заканчивается на первом
совпадении: дойди до страницы бронирования и посмотри, ЧЕЙ виджет там
инициализируется на самом деле. Остановка на первом маркере дала бы ложное
«данных нет» на объекте, который снимается целиком.

### Шаг 3. Добыть параметры рецепта БЕЗ браузера

Готовые пути по движкам — подробности в докстрингах `occupancy/probes/*.py`:

- **travelline / TL Integration** (`probes/travelline.py`): context
  `TL-INT-…` лежит в inline JS сайта; hotel_code резолвится чистым HTTP:
  `GET https://ru-ibe.tlintegration.ru/integration/profile/{context}/ru` →
  `booking-form.provider`. ВАЖНО: WAF Qrator отдаёт 403 на корень домена и
  угаданные пути — это НЕ значит, что API закрыт; реальные пути с
  браузерными Referer/Origin проходят. В headers рецепта Referer/Origin
  сайта обязательны.
- **bnovo / reservationsteps** (`probes/bnovo.py`): uid — из конструктора
  `BookingIframe({uid: "…"})` (обычно на `/booking`); `account_id` —
  числовой id аккаунта из скрытого поля формы листа ожидания на
  `rooms/index` (`<input name="account_id" value="11896">`): с ним пробник
  снимает фонд типов лёгким JSON `/v1/api/rooms`, без него — тяжёлым
  фолбэком по той же странице (у объектов с выключенным листом ожидания
  поля нет вовсе — проверка 15.08 на yck_kuzminskoe, это не ошибка);
  room_type_id категорий —
  СОЮЗ выдач `GET reservationsteps.ru/rooms/index/{uid}?lang=ru&dfrom=…&dto=…`
  на 2–3 пары заведомо свободных дат в РАЗНЫХ месяцах (сервер рендерит только
  доступные категории; в HTML — пары `data-category-id`/`data-name`).
  Нежилые категории («Подарочный сертификат») в рецепт не включать.
  Пустой `min_prices` на любые даты = модуль без тарифов (бронь живёт в
  другом канале): рецепт всё равно ok с оговоркой в notes — пробник честно
  даст sales_not_open (прецеденты: ok_reka, wood_glamp).
  ДВА СЛУЧАЯ, КОГДА ЦЕНОВОЙ ПУТЬ МЁРТВ, А МОДУЛЬ ЖИВОЙ (09.09.2026):
  (1) у аккаунта выключен показ цен в календаре (`has_to_show_calendar_prices
  = 0` в конфиге страницы виджета) — `min_prices` пуст на любые даты, а
  страница подбора остатки отдаёт: рецепт получает `params.grid_source:
  "rooms"`, и пробник строит сетку окнами в ОДНУ ночь по
  `/v1/api/rooms` (прецедент smr_shvedskie_dachi);
  (2) у объекта минимальный срок 2+ ночи — `min_prices` отдаёт null на весь
  горизонт: рецепт получает `params.min_stay` = найденный минимум, и та же
  ветка идёт окнами в min_stay ночей, а клетка честно значит «можно ли
  НАЧАТЬ заезд» (прецеденты _aferma_ 2 ноч., moreglamp.vip 2 ноч.,
  smr_dom_shalash_na_use 4 ноч.). Минимум ищется перебором окон 1-2-3-4
  ночи на 2-3 датах: окно короче минимума отдаёт «свободных нет» ВЕЗДЕ, и
  один замер отличить «распродано» от «минимум длиннее» не даёт.
  Обе ветки стоят запроса на ночь, поэтому глубина сетки у таких объектов
  равна горизонту ФОНДА (`--inventory-days`), а не 12 месяцам.
- **bronirui** (`probes/bronirui.py`): module_id — из `znmsWidget.init` в
  HTML; поля тела POST — snake_case (`module_id`, НЕ `moduleId` — на
  camelCase API отвечает ложным 401); календарь работает только с `number_id`
  конкретного номера — справочник номеров собирается союзом POST
  `/v2/numbers` на 2–3 пары дат; Origin/Referer сайта обязательны (домен
  проверяется по списку доверенных).
- **litepms** (`probes/litepms.py`): property_id — из litepms-виджета на
  странице бронирования (`litepms.ru/widget/calendar?id={property_id}`);
  больше ничего не нужно — календарь отдаётся готовым HTML без авторизации.
  Параметры лежат в inline-скрипте страницы (`var litepmsembed_id=…,
  litepmsembed_wid=…`), и у СЕТИ объектов аккаунт бывает один на всех, а
  площадки различает `wid` (villy_uley 09.09: id 5099, Волга wid 967,
  Карелия 988, Ока — wid пустой, календаря нет). Календарь без нужного `wid`
  отвечает 200 и телом «модуль бронирования отключен». Клетка `disabled` —
  ночь за краем открытого окна продаж (`sales_not_open`), а не занятая.
- **homereserve** (`probes/homereserve.py`): token — из
  `initWidgetSearch({token})`; две POST на `realtycalendar.ru/v2/widget/{token}/`
  (`apartments` — справочник домиков, `calendar` — посуточно); единица
  продажи уже конкретный домик, фонд снимать нечем и не нужно.
- **uhotels** (`probes/uhotels.py`): токен отеля — из конфигурации `w.artDg`
  в inline JS страницы `/booking` (поле `hotel`, вид `<id>:<hash>`); дальше
  POST `api.uhotels.app/api/widget/v1/booking/rooms` с телом JSON
  `{hotel, lang, currency, dateIn, dateOut, days, rooms:[{adults,children}]}`
  — на ночь отдаёт список категорий, где поле `max` это ОСТАТОК ДОМИКОВ.
  Метод `save` — оформление брони, не звать никогда.

### Шаг 3а. Фонд типов: несколько одинаковых домиков под одним названием

В одном глэмпинге часто стоит несколько одинаковых домиков, и модуль продаёт
их ОДНИМ типом («А-фрейм», «Этнодом»). Календарь такого типа отвечает лишь
«свободно ли хоть что-то», поэтому без фонда день типа считается занятым,
только когда продан ПОСЛЕДНИЙ домик, — занятость занижается (замер 15.08 на
одном TL-объекте, 16–29.08: 24% по типам против ≥30,4% по домикам; тип из
трёх домиков показывал 0% за две недели, хотя продавался четыре ночи).

Кто отдаёт остаток номеров:

| Движок | Где остаток | Цена |
|---|---|---|
| travelline (TL Integration) | `BookingForm/hotel_availability`, поле `limited_inventory_count` категории; категории нет в ответе — продана целиком | POST на ночь |
| bnovo / reservationsteps | `GET /v1/api/rooms?account_id=…&dfrom=…&dto=…`, поле `available`; фолбэк без account_id — `data-available` в селектах страницы `rooms/index` | запрос на ночь |
| bronirui | остаток не нужен: `number_id` — уже конкретный номер | 0 |
| litepms | остаток не нужен: `room-item` — уже конкретный номер | 0 |
| homereserve | остаток не нужен: `apartment` — уже конкретный домик | 0 |
| uhotels | приходит ДАРОМ: поле `max` в том же ответе `rooms`; категории нет в ответе — продана целиком | 0 |

Пробники делают это сами; разведчику важно положить в рецепт `account_id`
(bnovo) и `hotel_code` (travelline). Ограничения метода, которые НЕ
скрываются: у TL счётчик приходит, только когда свободных мало, — фонд
берётся как максимум наблюдённого остатка, то есть оценка снизу; если
календарь и остаток спорят (min-stay, ограничение по гостям), клетка
остаётся бинарной. Объект, у которого фонд не снялся, помечается в сводке
«по типам» — цифра занижена, и это видно читателю.

### Шаг 4. Если HTTP не хватило — Playwright, строго последовательно

Один объект за раз, одна вкладка. Открой страницу бронирования, дождись
виджета, сними из сетевого трафика живой JSON-запрос календаря и сверни его
в рецепт (шаблон URL/тела + правило подстановки дат). Браузер — последний
довод: сначала исчерпай пути шага 3.

### Шаг 5. Немедленная проверка рецепта

Записал рецепт в реестр → сразу прогони (щадяще, ОДИН прогон на объект):

    .venv/bin/python occupancy/cli.py --probe <username>

Затем сверь результат с виджетом на глаз: открой календарь на сайте и
сличи 2–3 даты (занятые пары пт–сб, свободные будни). Расходится — рецепт
не готов: разбирайся, а не записывай.

### Шаг 6. Запись в реестр

Формат — SCHEMA (а) в `occupancy_core.py`. Обязательно заполни: `site`,
`engine`, `status`, `request` (url_template/method/params/headers/
date_substitution — так, чтобы пробник воспроизвёл без тебя), `discovered_at`,
`notes` (что нашёл, какие грабли, результат живого прогона), `source_urls`
(правило №1 — evidence). У `broken` — обязателен `broken_reason`.

## Объект без модуля → агрегаторы

Модуля на сайте нет (или сайта нет вообще) — ищи календарь объекта на
агрегаторах, по очереди: Островок (ostrovok.ru), Суточно.ру (sutochno.ru),
Яндекс.Путешествия (travel.yandex.ru). Поиск — по названию объекта и гео;
у Островка есть подсказки `GET /api/site/multicomplete.json?query=…` (отдаёт
master_id и слаг отеля без браузера).

- **Найден на Суточно.ру** → обычный машинный рецепт `engine: "sutochno"`,
  `status: "ok"`, `params.objects = {"<object_id>": {...}}` (object_id — из
  адреса объявления `<город>.sutochno.ru/<id>`). Снимает таймер; цифра всё
  равно помечена `aggregator_quota` и с модульными медианами не смешивается.
- **Календарь найден на Островке/Яндексе** → рецепт с `engine: "aggregator-<платформа>"`
  (aggregator-ostrovok, aggregator-sutochno, aggregator-yandex-travel),
  `status: "aggregator"` и ОБЯЗАТЕЛЬНОЙ маркировкой в notes: «квота
  агрегатора, не полная загрузка» — объект отдаёт агрегатору часть фонда,
  и его занятость там не равна загрузке в директе. В снапшоте такого объекта
  всегда `source_kind: "aggregator_quota"` — сводка никогда не смешивает эти
  цифры с модульными без пометки.
- **Нет и на агрегаторах** → `status: "no_module"` с причиной «бронь только
  в директе/телеграме» в notes. Это не провал, а факт для интервью: у
  владельца нет измеримого контура атрибуции.

**Прогон агрегаторного рецепта — ручная ветка разведчика.** Пробников для
агрегаторов в v1 НЕТ (диспетчер `probes/__init__.py` их не знает) — это
осознанно: агрегаторных объектов 1–2, антибот у платформ злее модульных
движков, и дешевле исполнить рецепт браузером при прогоне, чем строить и
чинить пробник. При прогоне разведчик открывает страницу отеля с датами
(url_template рецепта), читает доступность/цены по юнитам и кладёт сетку в
снапшот через ядро — fixture-режимом CLI:

    .venv/bin/python occupancy/cli.py --fixture <сетка.json>

(объект сетки — SCHEMA (б) с `source_kind: "aggregator_quota"`; образец
полного прохода — glamping_pod_nebom, 14.08). Агрегаторы показывают остаток
номеров прямо в выдаче («осталось 4 номера» у Островка) — переноси его в
клетку парой `units_total`/`units_free`, иначе тип с четырьмя одинаковыми
тентами снова посчитается за один домик. Сломался агрегаторный рецепт
(капча, смена вёрстки) — `status: "broken"` и переразведка, не обход.

## Запреты

Железно, в обоих звеньях (спека, решение оператора 14.08):

- НЕ бронировать. Никаких шагов дальше просмотра календаря; эндпоинты
  бронирования (`order/*` и подобные) не зовутся никогда.
- Формы НЕ сабмитить (включая «запросить бронь», лид-формы, листы ожидания).
- Капчи и антибот НЕ обходить. Упёрся (SmartCaptcha, Qrator-челлендж,
  403 на реальных путях) — честный `insufficient_data` с причиной; для
  рецепта — `broken` с `broken_reason`. Никаких прокси, фингерпринт-трюков
  и повторных штурмов.
- Паузы ≥ 1.2 с между запросами к одному хосту, таймауты щадящие, ретраев
  нет: один запрос — одна попытка.
- Плохой ответ данных — не повод донимать хост: статус `insufficient_data`
  и причина, дальше по списку.

## Прогон

Полный цикл одной командой: очередь целей → пробники/разведка → ОДИН снапшот
→ сводка → артефакт по стабильному url → запись в CF Run Log. Прогон НЕ
падает из-за отдельного объекта: всё, что не снялось, становится честной
строкой insufficient_data с причиной — и в снапшоте, и в сводке.

### Шаг 0. Зафиксируй старт

ПЕРЕД работой сними момент старта для Run Log (правило №6 завода):

    date -u +%Y-%m-%dT%H:%M:%S+00:00

### Шаг 1. Очередь целей

Аргумент команды — список username (через пробел/запятую) — сужает прогон.
Без аргумента цели — ВСЕ username из `targets.json` (порядок строк файла =
важность, см. его `_note`; это же порядок строк сводки).

Цель с `"reference": true` — объект-ОРИЕНТИР, а не кандидат в клиенты
(16.08: pineriver_hotel, отель на 180 домиков). Снимается наравне со всеми,
но в сводке помечен «референс», стоит последней строкой, не входит в
знаменатель «снято N из M целей» и вместо вердикта про оффер получает
строку про роль. Ставить такие цели в КОНЕЦ файла.

Цель с `"notify": true` — после каждого ПЛАНОВОГО прогона о ней уходит
короткая сводка в телеграм (`occupancy/tg_digest.py` собирает текст,
`cf.notify` отправляет — внешний пакет, в витрине отсутствует, без него уведомление
просто не уходит; `"changes"` вместо `true` — писать только когда
календарь двигался или снимок неполный). Человеческое имя для сообщения —
поле `"title"`. О пропаже данных сообщение уходит ВСЕГДА, в любом режиме:
это единственная новость, которая требует человека.

### Шаг 2. Разбор очереди по реестру

Прочитай `recipes.json` и разложи цели на три ветки:

- **Рецепт `ok`** → в пробный вызов (шаг 3), разведка не нужна.
- **Рецепта нет или `broken`** → ОДНА попытка переразведки по разделу
  «Разведка объекта» выше (строго последовательно, один объект за раз;
  у broken начни с `broken_reason` — там записано, что сломалось). Дала
  ok-рецепт → объект в пробный вызов. Не дала (модуль всё ещё выключен
  отелем, движок не поддержан v1, no_module) — это подтверждённый статус,
  не падение: объект ВСЁ РАВНО идёт в пробный вызов — CLI сам запишет его
  insufficient_data с причиной («рецепта нет в реестре», «рецепт помечен
  broken»); обнови notes рецепта датой и итогом проверки.
- **Рецепт `aggregator`** → браузерная ветка (раздел «Объект без модуля»):
  открой страницу из `url_template` рецепта, сними доступность по юнитам и
  сложи сетку в файл-фикстуру (SCHEMA (б), `source_kind: "aggregator_quota"`)
  в scratchpad. Капча/смена вёрстки → рецепт `broken` + фикстура-объект со
  `status: "insufficient_data"` и причиной — строка в снапшоте обязана быть.

### Шаг 3. Один снапшот на прогон

Все `--probe` и `--fixture` — ОДНИМ вызовом CLI (иначе прогон рассыплется на
несколько каталогов-снапшотов и динамика поедет):

    .venv/bin/python occupancy/cli.py \
        --probe <u1> --probe <u2> ... [--fixture <агрегаторная-сетка.json> ...]

CLI пишет каталог `snapshots/<YYYY-MM-DD-HHMM>/`, печатает строку сводки по
каждому объекту и строки динамики против предыдущего снапшота; рецепты со
сменой схемы/антиботом сам помечает broken (сигнал переразведки следующему
прогону).

**Про время и горизонты (редакция 04.09).** Горизонт скользящий от сегодня и
двухслойный: СЕТКА (докуда спрашиваем доступность) — 12 месяцев; ФОНД (докуда
спрашиваем «сколько домиков типа свободно») — 45 ночей, ключ `--inventory-days`.
Фонд стоит одного запроса на ночь у TravelLine/Bnovo/UHotels и составляет почти
всю цену прогона; глубже 45 ночей клетка бинарна и помечается «фонд не снимался»
(поле `inventory_until` объекта). Замер 04.09: 58 целей за 53 минуты при
параллелизме по хостам (`--host-workers`, пауза 1,2 с держится ВНУТРИ хоста
замком, между хостами очереди идут одновременно). У TravelLine календарь и
booking_rules на диапазон длиннее ~91 суток отвечают пустотой — пробник режет
их окнами по 90 суток (`RULES_WINDOW_DAYS`); это наш регресс 04.09, вылезший
в первом же годовом прогоне, не вендор.

Прогон пишет объект на диск СРАЗУ после съёма (`run.json` — в начале, итог —
в конце), держит дедлайн `--deadline-min` (90 при TimeoutStartSec=120) и бюджет
на цель; второй одновременный живой съём на машине отказывается стартовать
(замок `.probe-hosts.lock` — паузу к чужому хосту процессы не делят). Рецепт
ломается только сменой схемы; 403/429/заслон считаются сутками подряд и ломают
на третьи (`refusals` в рецепте).

### Шаг 4. Сводка

    .venv/bin/python occupancy/build_summary.py

Собирает из ВСЕЙ истории снапшотов (последний снимок каждой цели + динамика
против её предыдущего) два файла: человеческую сводку
`docs/research/2026-08-10-glamping-market/occupancy.md` и html той же сводки
для артефакта `agent-runtime/research/glamping/occupancy/occupancy-artifact.html`
(оба каталога в витрине отсутствует; пути задаются ключами `--out`/`--out-html`).

### Шаг 5. Артефакт по стабильному url

Метафайл `docs/research/2026-08-10-glamping-market/occupancy-artifact.json`
(`{"url", "created_at"}`; в витрине отсутствует) — единственный источник адреса страницы:

- файла НЕТ (первый прогон) → загрузи скилл `artifact-design` (правило
  харнесса — до записи страницы), опубликуй html инструментом Artifact
  (favicon 🏕, title уже в html) и запиши в метафайл url и момент создания;
- файл ЕСТЬ → опубликуй html с `url` из метафайла — страница обновится по
  ТОМУ ЖЕ адресу. Новый артефакт не создавать никогда: у руководителя одна
  постоянная ссылка.

### Шаг 6. Run Log

(`cf` — журнал прогонов внешнего контура, в витрину не входит; вызов best-effort.)

    .venv/bin/python -m cf log-run --agent glamping-occupancy \
        --status success --started-at <ISO из шага 0> \
        --input "<цели прогона>" \
        --outputs "<каталог снапшота>" "occupancy.md" "<url артефакта>"

`--status insufficient_data` — когда данных не снялось ни с одного объекта.

### Прогон по расписанию (без агента)

С 16.08 цифры не ждут агента: user-таймер `cf-occupancy.timer` раз в сутки в
06:30 зовёт `occupancy/run_scheduled.py` — тот прогоняет пробники, пересобирает
сводку, шлёт уведомления по целям с `notify` и пишет строку в Run Log. Юниты —
`deploy/systemd-user/`, ставятся без sudo (`systemctl --user`), к паузе
заводских таймеров отношения не имеют.

Очередь таймера — только цели, чей движок умеет снимать пробник; агрегаторы,
чужие движки вне v1 и объекты без рецепта он ПРОПУСКАЕТ и печатает почему.
Это не лень, а защита данных: пустой снимок «движок не поддержан» становится
последним и затирает в сводке живые цифры, которые агент до того снял
браузером (ровно так 18.08 пропали Островок-квоты glamping_pod_nebom и
hobbitland.ru). Цели с `broken` в очереди ОСТАЮТСЯ: их строка «нужна
переразведка» и есть сигнал позвать агента.

Что таймер НЕ делает и что остаётся агенту: разведка объектов без рецепта и
с `broken`, браузерная ветка агрегаторов и ПУБЛИКАЦИЯ артефакта. То есть
между прогонами агента данные и `occupancy.md` свежие, а страница по
постоянной ссылке — от последнего прогона агента; освежить её = шаг 5.

Ручной вызов того же самого: `.venv/bin/python
occupancy/run_scheduled.py [--dry-run]`.

### Третий трек: топ-50 глэмпингов России по Instagram (с 08.09)

Поручение заказчика 07.09.2026: топ-50 глэмпингов России по подписчикам в
Instagram на ежедневной слежке, цель — «какие юниты сдаются лучше всего и
почему». Отбор — `agent-runtime/research/glamping/ru-top50/` (в витрине отсутствует; Apify: поиск по
140 запросам + 29 хэштегов + профили; `rank_candidates.py` сливает
кандидатов, классификация «глэмпинг ли, в России ли» — агентами по партиям,
факты без оценок качества). Все 50 целей имеют `cohorts: ["ru50"]` и
`cohort_details.ru50` (место, Instagram, число подписчиков и источник отбора).
Новые цели идут в тот же `targets.json` с `region: "ru50"`; четыре уже
наблюдаемых объекта сохраняют ключ и прежний регион. В частности,
`alpha.glamping` — это `smr_alfa_glemping`, `smolkino2019` —
`smr_smolkinoecovillage`. Это одна цель и одна история, а не второй объект.
Региональная сводка ru50 содержит только новые цели; все 50 сравниваются по
явной принадлежности к когорте, а региональные медианы не смешиваются.
Рецепты — `occupancy/scout.py` по сайту и перенос черновиков
в реестр одной командой:

    .venv/bin/python occupancy/scout_apply.py --manifest <json> --verification <json> [--with-honest] [--dry-run]

`scout_apply` берёт в реестр только `verdict: high` со статусом ok и
успешной проверкой того же `recipe_hash` (ok/partial, известные клетки), действующие
ok-рецепты не затирает (`--force`), low/refuse печатает списком на доразведку
(с `--with-honest` — честной записью no_module/broken, чтобы цель не пропала
из сводки) и ОТКАЗЫВАЕТСЯ работать, пока идёт прогон (настоящие flock реестра
и снапшотов или открытый снапшот) — грабля 04.09 20:25. Наличие оставшегося
файла `.run.lock` само по себе не доказывает работающий процесс. CAPTCHA,
ошибка сети или отсутствие сайта — broken/неизвестно, не доказанное no_module.

Пробники, подключённые 08.09: `bookonline24`, `frontdesk24`, `rc-bookings`,
`sutochno`. У rc-bookings ключи квартир — физические юниты, у BookOnline24 и
Frontdesk24 — категории. `frontdesk24.request.params.include_room_types`
позволяет явно выбрать непустой список ID категорий; без этого параметра
снимается весь комплекс. Пропавший выбранный ID остаётся unknown.
Суточно всегда возвращает `source_kind: "aggregator_quota"`, включая отказ;
его квота не входит в медианы прямых модулей. ВАЖНОЕ СЛЕДСТВИЕ для ветки
«объект без модуля» ниже: у Суточно, в отличие от Островка и Яндекса,
пробник ЕСТЬ — значит объект, найденный на Суточно, получает обычный рецепт
`engine: "sutochno"` со `status: "ok"`, и его снимает таймер, а не агент
браузером (прецеденты 09.09.2026: elki_igolki_aglos, smr_foxway, smr_duby).
Поэтому среди трёх агрегаторов Суточно ищется ПЕРВЫМ. Неизвестный тип блока на
Суточно означает unknown, а не проданную ночь. Закрытый горизонт продаж
отличается от занятой ночи. Короткая проверка подключения не подменяет
дневной снимок и не создаёт историю сезонности.

Цена третьего трека — время прогона: узкое место не число хостов, а общие
API-хосты движков (все Bnovo — один хост, все TravelLine — один), поэтому
дедлайн прогона поднят до 150 мин, `TimeoutStartSec` до 180, публикация
страниц сдвинута на 09:45 (08.09.2026).

### Запреты прогона

Все «Запреты» выше действуют и здесь дословно. Дополнительно к прогону:

- Playwright (агрегаторы, переразведка) — строго последовательно, один
  объект за раз, одна вкладка.
- Один повтор на объект максимум: не снялось после переразведки — честный
