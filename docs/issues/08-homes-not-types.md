# 08 — Считать домики, а не типы размещения

**Статус:** сделано 15.08.2026
**Повод:** вопрос заказчика 15.08: «в одном глэмпинге может быть несколько домов
одного типа и названия, понимает ли он это при анализе загруженности».

## Что было не так

Ответ: не понимал. У TravelLine и Bnovo единица сетки — ТИП размещения, а не
физический домик. Календарь такого типа отвечает только «свободно ли хоть
что-то», поэтому день типа помечался занятым, лишь когда продан ПОСЛЕДНИЙ
домик. Это то же самое смещение, которое тикет 02 поймал этажом выше (у
агрегатного календаря TravelLine), — внутри типа его не заметили: ни в спеке,
ни в тикетах, ни в проверках честности сводки слова про несколько одинаковых
домиков не было.

Затронуто 13 из 17 рабочих рецептов (10 travelline + 3 bnovo).

Замер на одном TL-объекте (14 ночей 16–29.08.2026, живые ответы
`hotel_availability`; названия категорий обезличены):

| | по типам (было) | по домикам (стало) |
|---|---|---|
| весь объект | 24,0% | ≥30,4% |
| тип A (2 номера) | 7% | 25% |
| тип B (2 номера) | 29% | 43% |
| тип C (≥3 номера) | 0% за две недели | продавался 4 ночи подряд |

Отдельным дефектом: в `probes/bronirui.py` номера складывались в сетку по
ИМЕНИ, поэтому три одинаковых «A-frame дом» схлопывались в один юнит —
занятый номер пропадал молча, вместе с уже сделанным запросом. У travelline и
litepms дедуп был, здесь его забыли.

## Что сделано

1. **Схема (SCHEMA (б))**: клетка получила необязательную пару
   `units_total`/`units_free` — сколько домиков в типе продаётся в эту ночь и
   сколько из них свободно. Валидатор требует пару целиком, согласие со
   `state` и `units_free <= units_total`.
2. **Метрика**: `occupancy_pct` считает домико-ночи (`core.cell_units`).
   Клетка без фонда весит один домик — старые снапшоты дают ровно прежние
   цифры. `core.unit_basis` отдаёт основу расчёта объекта
   (`unit`/`mixed`/`type`) и размер фонда.
3. **TravelLine**: шаг съёма остатков `BookingForm/hotel_availability`
   (`limited_inventory_count`), один POST на ночь горизонта сводки. Фонд типа
   = максимум наблюдённого остатка (оценка снизу: счётчик приходит, только
   когда свободных мало). Календарь и остаток спорят — клетка остаётся
   бинарной. Шаг вспомогательный: не снялся — `partial` с причиной, рецепт
   жив.
4. **Bnovo**: остатки из `GET /v1/api/rooms?account_id=…` (поле `available`),
   фолбэк без `account_id` — `data-available` в селектах страницы
   `rooms/index`. Проверено 15.08: JSON и HTML дают одно и то же
   (тип из нескольких домиков у Bnovo-объекта — 3 свободных), полностью занятая ночь отдаёт
   `rooms: []`.
5. **bronirui**: дубли имён различаются `number_id` («A-frame дом [731]»),
   каждая клетка несёт фонд 1. **litepms**: то же, фонд 1 на `room-item`.
6. **CLI**: `--no-inventory` — быстрый прогон без фонда (цифры занижены, и
   сводка это помечает).
7. **Сводка**: метка источника несёт «по домикам: N в M типах» / «по домикам
   частично» / «по типам (фонд не снят): занижение»; динамика показывает
   «допродано домиков в типах» — движение внутри типа, которого раньше не
   было видно вовсе; методика и проверки честности переписаны под поштучный
   учёт; календарные ленты красятся по домико-ночам, чтобы не расходиться с
   таблицей.

## Цена

Фонд стоит одного запроса на ночь: ~80 запросов и около двух минут на объект
при горизонте в три месяца (было три запроса и три секунды). Для 13 объектов
прогон вырастает примерно до получаса. Плата принята осознанно: дешевле у
движков остатки не отдают — параметр «сколько номеров» календарь TravelLine
игнорирует (проверено 15.08 на `rooms=2`), а у Bnovo `min_prices` про
количество не знает вовсе.
