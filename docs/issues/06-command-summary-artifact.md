# 06 — Слэш-команда целиком: прогон → сводка → артефакт → run-log

**What to build:** оркестрация `/glamping-occupancy [список|пусто=топ-30]` в
SKILL.md, замыкающая весь цикл одной командой: прочитать targets (аргумент
сужает), для каждого объекта — рецепт есть и жив → пробник; рецепта нет или
broken → разведчик (тикет 05) → пробник; снапшот прогона в историю; затем
сборка выходных слоёв:

1. markdown-сводка `occupancy.md` в docs/research рядом с отчётом волны 2 —
   человеческим текстом (правило «отчёты оператору»): таблица топ-30
   (загрузка авг/сен/окт, будни/выходные, динамика к прошлому снимку, статус
   источника: модуль/агрегатор-квота/no_module) + короткое досье на объект;
2. артефакт-страница с той же сводкой по СТАБИЛЬНОМУ url (url хранится в
   meta-файле рядом со сводкой; первый прогон создаёт артефакт и записывает
   url, последующие обновляют его же);
3. запись прогона в CF Run Log (`cf log-run --agent glamping-occupancy
   --started-at <ISO>` — правило №6).

Агрегаторные цифры в обоих слоях никогда не смешиваются с модульными без
пометки «квота»; все проценты подписаны «оценка сверху»; объекты без данных —
insufficient_data с причиной, не пропуск строки.

## Комментарии

Реализация: `occupancy/build_summary.py` (сборка сводки: markdown в docs/research
+ html артефакт-страницы), раздел «## Прогон» в SKILL.md (оркестрация:
старт-время → очередь целей → разбор по реестру с одной попыткой переразведки →
ОДИН вызов CLI со всеми --probe/--fixture → build_summary → артефакт по
метафайлу → cf log-run; запреты прогона), тесты
`tests/test_build_summary.py` (9 шт., чистая логика на fixture-снапшотах;
всего по скиллу 89 зелёных).

Решения:

- **Сводка собирается из ВСЕЙ истории снапшотов, не из последнего каталога.**
  Прогоны бывают узкими (аргумент-shortlist), а таблица обязана держать все
  24 цели: для каждой берётся её последний снимок по истории, динамика — против
  её же предыдущего. Колонка «Снят» показывает свежесть данных каждой строки.
- **Html артефакта генерирует скрипт** (в `agent-runtime/.../occupancy/
  occupancy-artifact.html`, правило №4), а не агент от руки: страница
  воспроизводима на каждом прогоне; публикация и метафайл
  `docs/research/2026-08-10-glamping-market/occupancy-artifact.json`
  ({url, created_at}) — шаг агента в SKILL.md. Стабильный url хранится в метафайле (создан смоуком 1, обновлён смоуком 2
  по тому же адресу; в витрине опущен).
- **Динамика строк без данных — «—»**, не «без изменений»: у insufficient_data
  нечему меняться, показывать нулевую динамику было бы ложным сигналом.
- Смоук вскрыл живую динамику даже за час: у одного объекта прибавилось
  четыре занятые даты между снимками 19:33 и 20:34 — подтверждение, что
  «загрузка устаревает за дни» из Problem Statement не преувеличение.
- Run Log: 7253a4112173 (смоук 1, старт 17:34:11Z) и f2e26ad5faaf (смоук 2,
  старт 17:36:01Z), оба `--agent glamping-occupancy` со started-at (правило №6).
- Переразведку broken второй смоук не повторял осознанно: broken подтверждён
  этим же сеансом часом ранее, второй заход к хосту нарушил бы щадящий режим;
  правило «одна попытка переразведки на прогон» в SKILL.md стоит.

**Задокументированное отступление (ревью 14.08): агрегаторная ветка ходит
браузером на каждый прогон.** Спека рисует разведчика, который заходит на
объект один раз и оставляет рецепт детерминированному пробнику; для
агрегаторных объектов прогон каждый раз исполняет рецепт браузером
(SKILL.md, «Прогон», шаг 2) и кладёт сетку fixture-режимом CLI. Это
осознанно: таких объектов в targets 1–2, антибот агрегаторов злее модульных
движков (щадящий режим запрещает и обход, и повторные штурмы — падать он
будет чаще), и строить пятый пробник ради пары строк дороже, чем исполнять
готовый рецепт браузером. «Один раз» при этом сохраняется для РАЗВЕДКИ:
браузер прогона лишь исполняет url_template готового рецепта, а не
разведует объект заново.
